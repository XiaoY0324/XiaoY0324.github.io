进程与线程

  • 进程是操作系统资源分配的基本单位，比如开个 qq，网页都是开了一个进程。
  • 线程是由进程所管理的，为了提升浏览器的稳定性和安全性，浏览器采用了多进程模型。

浏览器的(5个)进程

  • 浏览器进程：负责界面显示、用户交互、子进程管理，提供存储等。
  • 渲染进程：每个 tab 页都有单独的渲染进程，核心用于渲染页面。
  • 网络进程：主要处理网络资源加载(HTML、CSS,、JS等)，比如输入 url 时，需要去拉模板资源
  • GPU进程：3d 绘制，提高性能
  • 插件进程： chrome 中安装的一些插件

从输入 url 到浏览器显示页面发生了什么？

从进程的角度宏观分析整个流程~

  • 在浏览器进程中输入 url 地址开始导航，并准备渲染进程(进程之间的通信，采用的都是 ipc)
  • 在网络进程中发送请求，将响应后的结果交给渲染进程处理
  • 解析页面，加载页面中所需资源
  • 渲染完毕展示

我们开始细化每一步流程，并且从流程中提取我们可以优化的点。

输入内容判断

用户输入的是关键字还是 url，如果是关键字则使用默认调起搜索引擎去搜索关键字，如果是 url 则准备发送请求。

URL请求过程

  • 浏览器查找当前 url 资源是否存在缓存，如果有缓存、并且缓存未过期，直接从缓存中返回。
  • 查看域名是否已经被解析过了(浏览器缓存 -> 本机缓存 -> host 文件 -> 路由器缓存)，如果有缓存、并且缓存未过期，直接从缓存中返回，否则开始 DNS 协议进行域名解析。
  • DNS 是基于 udp 的哦，不会对数据进行分段传输，查找会先从根域名查找，(tcp 查询多级域名每次都要经过三次握手，tcp 传输比较慢，虽然安全可靠)，最后得到域名对应的 ip 地址，然后增加端口号。
  • 如果请求是 https，要进行 SSL 协商，保证数据的安全性。
  • 开始 ip 寻址(找到地址再握手)，请求排队，因为 http 1.1 限制同一个域名的请求数量不能超过 6 个 http 请求。
  • 排队后服务器创建 tcp 链接 （三次握手）
  • 利用 tcp 协议将大文件拆分成数据包进行传输(分段有序传输)，可靠的传输给服务器（丢包重传），tcp 层和 ip 层包装数据时会增加 tcp 报文头部，ip 头。
  • 发送 http 请求（请求行，请求头，请求体），服务器收到后会按照序号重排数据包。
  • HTTP 1.1 中支持 keep-alive 属性， TCP 链接默认不会立即关闭，后续请求可以省去建立链接时间。
  • 服务器响应结果（响应行，响应头，响应体），返回状态码为 301(永久重定向)、302(临时重定向，负载均衡的场景) 时，浏览器会进行重定向操作。（重定向会重新走以上这些流程，所以重定向性能不好）
  • 返回 304 则强制查找浏览器缓存。（服务端可以设置强制缓存）

至此，网页 html 返回完毕。

通过 network Timing 观察请求发出的流程：

  • Queuing: 请求发送前会根据优先级进行排队，同时每个域名最多处理 6 个 TCP 链接，超过的也会进行排队，并且分配磁盘空间时也会消耗一定时间。
  • Stalled : 请求发出前的等待时间（处理代理，链接复用）
  • DNS lookup : DNS 查找的时间
  • initial Connection :建立 TCP 链接时间
  • SSL: SSL 握手时间（SSL 协商）
  • Request Sent : 请求发送时间（可忽略）
  • Waiting(TTFB) : 等待响应的时间，等待返回首个字符的时间
  • Content Dowloaded : 用于下载响应的时间

蓝色：DOMContentLoaded : DOM 构建完成的时间
红色：Load: 浏览器所有资源加载完毕

渲染流程

  1. 浏览器无法直接使用 HTML，需要将 HTML 逐级转化成 DOM 树。（document）
  2. 浏览器无法解析纯文本的 CSS 样式，需要对 CSS 进行解析,解析成 styleSheets。CSSOM（document.styleSeets）
  3. 计算出 DOM树 中每个节点的具体样式（Attachment）
  4. 创建渲染（布局）树 renderTree，将 DOM 树中可见节点，添加到布局树中。并计算节点渲染到页面的坐标位置。（layout）
  5. 通过布局树，进行分层 （根据定位属性、透明属性、transform 属性、clip 属性，will-change 属性等）生成图层树
  6. 将不同图层进行绘制，转交给合成线程处理。最终生成页面，并显示到浏览器上 (Painting, Display)，这一步会生成各种绘制的代码，如下图。

http 版本区别

  • http 0.9 在传输过程中，没有请求头和请求体，服务器响应没有返回头信息，内容采用 ASCII 字符流来进行传输 HTML
    • 不能区分请求类型，只能传输 html
  • http 1.0 增加了请求头和响应头，实现多类型数据传输这种串行的传输，劣势有二：
    • 每次都要重新进行 tcp 三次握手，比较慢
    • 串行传输，一个传输完成，另一个才能开始传输
  • http 1.1，现在最常用的 http 版本。
    • keepa-live：默认开启持久链接(keep-alive)，在一个 TCP 链接上可以传输多个 http 请求
    • 单域名 6 链接：采用管线化的方式(分域名传输，每个域名能维护 6 个 TCP 持久链接，比如多个 cdn)
    • 存在队首阻塞：队首阻塞，虽然客户端可以并行发送多个请求，服务器端并行接收了多个请求，但由于要遵守 http 1.1 的规则，先接收到的请求需要先发送响应，造成了阻塞问题
    • 增加 cookie：为无状态的 http 增加了 cookie 和一些安全机制
  • http 2.0
    • 多路复用：因为 1.1 中的 6 个 TCP 连接都有 慢启动，多个 tcp 竞争带宽，队首阻塞等缺陷，这样 http2 就采用多路复用的机制，一个域名只开一个 TCP 长链接，我们可以通过一个 TCP 传输多个数据(通过二进制分帧层实现)，基于流，把不同类型的数据在一个 TCP 管道上进行分帧传输，服务端接收到之后按序号重组，收到请求的数据包信息。不过多路复用本质上只是缓解了 tcp 层的队首阻塞(tcp 连接没有那么多了)，但是并不能从本质上解决不同域名的队首阻塞。(一共只能 6 个 network 线程)
    • 服务器主动推送消息：之前的 TCP 发送消息包机制，都是一问一答，无法做到服务器主动给浏览器推送消息，http2 实现了它。
    • 头部压缩：通过 hpyck 算法，通过一个映射表把头部给映射为一个数字(压缩)
  • http 3.0 为了解决 tcp 队首阻塞问题，采用 QUIC 协议。QUIC 协议是基于 UDP 的(目前：支持和部署是最大的问题)
    • 不可靠的 udp：udp 不会创建 tcp 链接，也不保证消息可靠
    • 过往优化全部作废：以前对 tcp 所有的优化，全部作废了
  • HTTP 明文传输，在传输过程中会经历路由器、运营商等环节，数据有可能被窃取或篡改(安全问题)，所以后来有了 https，这里暂且不展开。

为什么 css 放到上面 js 放到下面呢？

href 和 src

  • href：是 hypertext reference 的缩写，表示超文本引用，用来建立当前元素和文档间的链接。常用的有 link，a，当 css 使用 href 引用，浏览器会识别该文档问 CSS，并行下载，不会停止对阻塞文档的解析。
  • src：是 source 的缩写，是资源，页面必不可少的一部分，src 指向的内容会嵌入到文档中当前标签的位置。常用的有 img, script, iframe。当 script 使用 src 引用，浏览器解析到该元素时会停止对文档的渲染，转而去处理脚本。需要注意的是，link 标签加载的 css 会阻塞 script 标签的执行，也就是说，如果 script 标签前面有 link 加载 css，会等待 css 加载完成(因为 js 也可能会操作样式，不然可能造成 js 操作样式后，样式表再操作一次，多次重绘)。

答案在这里

我们举一个例子：
一天，小明正在网上查找资料，项目中遇到的问题需要通过查阅资料来解决，他看到一个标题很有意思，觉得这应该是他要找的答案，于是他就点了进去，结果进入网站后几秒钟的时间，网页还是一片空白，过了好久才加载完成。为什么会出现这种情况？说到这那我们就有必要先了解一下网站加载的整个完整过程了。

  1. 首先浏览器从服务器接收到 html 代码，然后开始解析 html
  2. 构建 DOM 树（根据 html 代码自顶向下进行构建），并且在同时构建渲染树
  3. 遇到 js 文件加载执行，将阻塞 DomTree 的构建；遇到 css 文件，将阻塞 RenderTree 的构建，所以表象上看，link 标签写在 head 里，好像会等待 css 加载。

综上所述，script 标签最好放在 body 结束标签的前面，因为放在所有 body 中的标签后面就不会出现网页加载时出现空白的情况，可以持续的给用户提供视觉反馈，同时在有些情况下，会降低错误的发生。而 css 标签应该放在 head 标签之间，因为如果放在 body 结束标签的前面，那么当 DOM 树构建完成了，渲染树才构建，那么当渲染树构建完成，浏览器不得不再重新渲染整个页面，这样造成了资源的浪费。效率也不高。如果 css 放在 head 标签中，浏览器边构建边渲染，效率要高的多。

script 标签中的 defer 属性：构建 DOM 树的过程和 js 文件的加载异步（并行）进行，但是 js 文件执行需要在 DOM 树构建完成之后且 DOMContentLoaded 执行之前
script 标签中的 async 属性：构建 DOM 树、渲染树的过程和 js 文件的加载和执行异步（并行）进行），优先级较高，当两个同时设置时，async 会生效，除非浏览器不支持 async

DOMContentLoaded 和 load 事件

1.DOMContentLoaded 事件其实就是 dom 内容加载完毕，而这段时就是 HTML 文档被加载和解析完成。

2.页面上所有的资源（外链资源文件(包括 scripts)，图片，音频，视频等）被加载以后才会触发load事件，页面的load事件会在DOMContentLoaded被触发之后才触发。

Performance API

浏览器渲染的整个流程的加载图

关键时间节点 描述 含义
TTFB time to first byte(首字节时间) 从请求到数据返回第一个字节所消耗时间
TTI Time to Interactive(可交互时间) DOM树构建完毕，代表可以绑定事件
DCL DOMContentLoaded (事件耗时) 当 HTML 文档被完全加载和解析完成之后，DOMContentLoaded 事件被触发
L onLoad (事件耗时) 当依赖的资源全部加载完毕之后才会触发
FP First Paint（首次绘制) 第一个像素点绘制到屏幕的时间
FCP First Contentful Paint(首次内容绘制) 首次绘制任何文本，图像，非空白节点的时间
FMP First Meaningful paint(首次有意义绘制) 首次有意义绘制是页面可用性的量度标准
LCP Largest Contentful Paint(最大内容渲染) 在viewport中最大的页面元素加载的时间
FID First Input Delay(首次输入延迟) 用户首次和页面交互(单击链接，点击按钮等)到页面响应交互的时间

通过 performance API 计算这些属性~

code 
<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="UTF-8">
  <meta http-equiv="X-UA-Compatible" content="IE=edge">
  <meta name="viewport" content="width=device-width, initial-scale=1.0">
  <title>Document</title>
</head>
<body>
  <div style="background: red; width: 100px; height: 100px;"></div>
  <h1 elementtiming="meaningful">有意义的元素</h1>
  <!-- 需要等待所有的事件执行完毕后才能计算 -->
  <script>
    window.addEventListener('DOMContentLoaded', function() {
      setTimeout(() => {
        document.body.appendChild(document.createTextNode('FCP 有内容的绘制'));
      }, 1000);
    });
    setTimeout(() => {
      const { 
        fetchStart, // 开始加载 app
        requestStart, // 开始发送请求，加载数据
        responseStart, // 响应刚开始返回，计算首字节返回时间
        responseEnd, // 响应结束
        domInteractive, // dom 可交互的时间点(可以绑定事件了)
        domContentLoadedEventEnd, // dom 绘制完毕
        loadEventStart // load 事件执行，代表外链资源也加载完毕
      } = performance.timing; 

      // 首字节时间(响应开始时间 - 请求开始时间)，表示了服务器的处理能力
      let TTFB = responseStart - requestStart;

      // 可交互时间(dom 可交互时间 - 开始加载 app 时间)
      let TTI = domInteractive - fetchStart;

      // dom 渲染完毕用时 (domContentLoadedEventEnd 时间 - 开始加载 app 时间)
      let DCL = domContentLoadedEventEnd - fetchStart;

      // 所以资源加载完毕用时 (加载完毕时间 - 开始加载 app 时间)
      let L = loadEventStart - fetchStart;

      console.log(TTFB, TTI, DCL, L);

      // 绘制相关属性
      const paint = performance.getEntriesByType('paint'); // 具体的 api 查看 MDN

      let FP = paint[0].startTime; // 首次绘制
      console.warn('FP 首次绘制', paint[0].startTime); // 页面有元素即可

      let FCP = paint[1].startTime; // 有内容的绘制
      console.warn('FCP 有内容的绘制', paint[1].startTime); // 页面必须有内容
    }, 3000);

    // FMP 首次有意义的绘制
    new PerformanceObserver((entryList, observer) => {
      let FMP = entryList.getEntries()[0].startTime;

      console.log('FMP 首次有意义的绘制',FMP);
      observer.disconnect(); // 结束监控
    }).observe({ entryTypes: ['element'] }); // 观测所有元素

    // LCP 最大内容绘制
    new PerformanceObserver((entryList, observer) => {
      let entries = entryList.getEntries();

      // 取最后一个
      let LCP = entries[entries.length - 1];

      console.log('LCP 最大的内容', LCP);
      observer.disconnect(); // 结束监控
    }).observe({ entryTypes: ['largest-contentful-paint'] }); 

    // FID (真正的响应执行 - 触发动作时间) 用户首次和页面交互(单击链接，点击按钮等)到页面响应交互的时间
    new PerformanceObserver((entryList, observer) => {
      let firstInput = entryList.getEntries()[0];

      if (!firstInput) return; 

      // 点击开始到真正的响应执行开始
      let FID = firstInput.processingStart - firstInput.startTime;

      console.log('FID 首次输入延迟', FID);
      observer.disconnect(); // 结束监控
    }).observe({ type: ['first-input'], buffered: true }); 

  </script>
</body>
</html>


优化策略

网络优化

  • 减少 HTTP 请求数，合并 JS、CSS, 合理内嵌 CSS、JS。
  • 合理设置服务端缓存，提高服务器处理速度。 (强制缓存、对比缓存)
  • 避免重定向，重定向会降低响应速度 (301, 302)
  • 使用 dns-prefetch,进行 DNS 预解析
  • 采用域名分片技术，将资源放到不同的域名下。接触同一个域名最多处理 6 个 TCP 链接问题。
  • 采用 CDN 加速加快访问速度。(指派最近、高度可用)
  • gzip 压缩优化，对传输资源进行体积压缩 (html, js, css)
  • 加载数据优先级 : preload(预先请求当前页面需要的资源)，prefetch(将来页面中使用的资源)，将数据缓存到 HTTP 缓存中

关键渲染节点优化


比如后续有些 js 操作，会引起样式计算，重排，重绘，合成步骤。

  • 引起重绘的操作：不影响它在文档流中位置的操作，比如页面中元素背景颜色的改变。
  • 引起重排(回流)的操作：添加元素、删除元素，修改大小，移动元素位置，获取位置相关信息(浏览器为了给到我们准确的更新后的位置信息，会进行重排)等。

我们应当尽可能减少重绘和重排

1. 强制同步布局问题

JavaScript 强制将计算样式和布局操作提前到当前的任务中，比如给 app 元素添加了个子节点，又在函数中做了获取 app 元素位置操作，强行令浏览器先同步计算样式 -> 重排，然后再进行函数的获取位置操作。

<div id="app"></div>
<script>
function reflow() {
    let el = document.getElementById('app');
    let node = document.createElement('h1');
    node.innerHTML = 'hello';
    el.appendChild(node);
    // 浏览器不知道插入子节点后 app 位置改变没有
    // 本来应该在之后函数执行完毕进行布局的，在这里强制同步布局
    console.log(app.offsetHeight);
}

requestAnimationFrame(reflow);
</script>

解决方法是读写分离，比如读取操作放在函数外，确信元素位置不会发生改变的话，先读再操作元素。

2. 更严重的布局抖动问题

在一段 js 代码中，反复执行布局操作，就是布局抖动

function reflow(){
    let el = document.getElementById('app');
    let node = document.createElement('h1');
    node.innerHTML = 'hello';
    el.appendChild(node);
    // 强制同步布局
    console.log(app.offsetHeight);
}
window.addEventListener('load',function(){
    for(let i = 0 ; i<100;i++){
        reflow();
    }
});

3. 怎么减少回流和重绘呢？

  • 脱离文档流，比如绝对定位
  • 渲染时给图片增加固定宽高(给 img 设置固定的宽高占位)，以免图片加载出来时撑起布局，引起回流)
  • 尽量使用 css3 动画(直接在合成节点「GPU 加速」做的绘制和合成，而且会生成新的图层)
  • 可以给元素添加 will-change 属性提取到单独的图层中
    // 标识这个元素后面可能会变化，需要提前提取到单独的图层。
<div style="will-change: transform">

静态文件优化

图片相关优化

图片格式优化

  • jpg: 适合色彩丰富的照片、banner 图；不适合图形文字、图标（纹理边缘有锯齿），不支持透明度
  • png: 适合纯色、透明、图标，支持半透明；不适合色彩丰富图片，因为无损存储会导致存储体积大
  • gif: 适合动画，可以动的图标；不支持半透明，不适和存储彩色图片
  • webp: 适合半透明图片，可以保证图片质量和较小的体积
  • svg 格式图片: 相比于 jpg 和 jpg 它的体积更小, 渲染成本过高,适合小且色彩单一的图标;

图片优化

  • 避免空 src 的图片(也会发送请求的)
  • 减小图片尺寸，节约用户流量
  • img 标签设置 alt 属性， 提升图片加载失败时的用户体验
  • 原生的 loading:lazy 图片懒加载(可视区域内才会加载，兼容性还可以，但是什么时候加载不可控)
    <img loading="lazy" src="./images/1.jpg" width="300" height="450" />
  • 不同环境下，加载不同尺寸和像素的图片
    <img src="./images/1.jpg" sizes="(max-width:500px) 100px,(max-width:600px) 200px"  srcset="./images/1.jpg 100w, ./images/3.jpg 200w">
  • 对于较大的图片可以考虑采用渐进式图片(先给模糊图)
  • 采用 base64URL 减少图片请求(体积比以前大 1/3)
  • 采用雪碧图合并图标图片等(现在用的不多了)

html 优化

  • 语义化 HTML: 代码简洁清晰，利于搜索引擎，便于团队开发
  • 提前声明字符编码，让浏览器快速确定如何渲染网页内容
  • 减少 HTML 嵌套关系、减少 DOM 节点数量
  • 删除多余空格、空行、注释、及无用的属性等
  • HTML 减少 iframes 使用 (iframe 会阻塞父级页面 onload 事件可以动态加载 iframe，比如刚开始给个空标签，后面再去赋值 src)
  • 避免使用 table 布局(阅读性差)

css 优化

  • 减少伪类选择器、减少样式层数、减少使用通配符(底层会逐层匹配)
  • 避免使用 CSS 表达式，CSS 表达式会频繁求值， 当滚动页面，或者移动鼠标时都会重新计算 (IE6, 7 下有效果)
    background-color: expression((new Date()).getHours() % 2 ? "red" : "yellow" );
  • 删除空行、注释、减少无意义的单位、css 进行压缩
  • 使用外链 css,可以对 CSS 进行缓存
  • 添加媒体字段，只加载有效的 css 文件，从整体代码中抽离出去
    <link href="index.css" rel="stylesheet" media="screen and (min-width:1024px)" />
  • CSS contain属性,将元素进行隔离，不影响后续元素
  • 减少 @import 使用，由于 @import 采用的是串行加载(依次加载)，而 link 标签是并行加载

contain 属性允许开发者声明当前元素和它的内容尽可能的独立于 DOM 树的其他部分。这使得浏览器在重新计算布局、样式、绘图、大小或这四项的组合时，只影响到有限的 DOM 区域，而不是整个页面，可以有效改善性能，比如 layout 值，表示元素外部无法影响元素内部的布局，反之亦然。

js 优化

  • 通过 async、defer 异步加载文件(蓝色代表 js 加载，红色代表 js 执行)，可以看到 async、defer 都是异步加载 js 文件，只不过 defer 会延后执行。
  • 减少 DOM 操作，缓存访问过的元素(虚拟 dom 就是干这个的，操作不直接应用到DOM上，而应用到虚拟DOM上。最后一次性的应用到DOM上)。
  • 使用 webworker 解决程序阻塞问题。
  • IntersectionObserver 实现延迟加载(替换 onscroll 事件，例子在后面)
  • 虚拟滚动 vertual-scroll-list(基于上述延迟加载实现，只显示可视区域内的，外部的删除或者隐藏掉)
  • requestAnimationFrame、requestIdleCallback，由于每帧大约 16.6ms(60fps 情况下)，但并不一定是 16.6，所以定时去更新动画不准确(会丢帧)，requestAnimationFrame 可以让我们在每帧开始做点事情，requestIdleCallback 则可以让我们在每帧空闲的时候做事情。
  • 尽量避免使用eval, 消耗时间久
  • 使用事件委托，减少事件绑定个数。
  • 尽量使用 canvas 动画、CSS 动画(尽量不要 js 动画)

        const observer = new IntersectionObserver(function(changes) { 
            changes.forEach(function(element, index) {
                if (element.intersectionRatio > 0) { // 进入可视区域后
                    observer.unobserve(element.target); // 停止观测该图片

            });
        }

        let start;

        function step(timestamp) {
            if (start === undefined)
                start = timestamp;
            const elapsed = timestamp - start;
            element.style.transform = 'translateX(' + Math.min(0.1 * elapsed, 800) + 'px)';
            if (elapsed < 2000) { 
                window.requestAnimationFrame(step);
            }
        }
        window.requestAnimationFrame(step);


        function sleep(d) {
            for (var t = Date.now(); Date.now() - t <= d;);
        }
        const tasks = [
            () => {
                console.log("task1");
                sleep(10);
            },
            () => {
                console.log("task2");
                sleep(10);
            },
            () => {
                console.log("task3");
                sleep(10);
            },
        ];
        requestIdleCallback(taskLoop, { timeout: 1000 })
        function taskLoop(deadline) {
            console.log('本帧剩余时间', deadline.timeRemaining());
            while ((deadline.timeRemaining() > 1 || deadline.didTimeout) && tasks.length > 0) {
                performUnitOfWork();
            }
            if (tasks.length > 0) {
                console.log(`只剩下${deadline.timeRemaining()}ms,时间片到了等待下次空闲时间的调度`);
                requestIdleCallback(taskLoop);
            }
        }
        function performUnitOfWork() {
            tasks.shift()();
        }


    </script>

优化策略总结

  • 关键资源个数越多，首次页面加载时间就会越长
  • 关键资源的大小，内容越小，下载时间越短
  • 优化白屏：内联 css 和内联 js 移除文件下载， 较小文件体积
  • 预渲染，打包时进行预渲染
  • 使用 SSR 加速首屏加载（耗费服务端资源），有利于 SEO 优化。 首屏利用服务端渲染，后续交互采用客户端渲染

结合浏览器存储来优化

  • cookie: cookie 过期时间内一直有效，存储大小4k左右、同时限制字段个数，不适合大量的数据存储，每次请求会携带cookie,主要可以利用做身份检查。
    • 设置 cookie 有效期
    • 根据不同子域划分 cookie，较少传输
    • 静态资源域名和 cookie 域名采用不同域名，避免静态资源访问时携带 cookie
  • localStorage: chrome 下最大存储 5M, 除非手动清除，否则一直存在。利用 localStorage 存储静态资源
    function cacheFile(url) {
  let fileContent = localStorage.getItem(url);
  if (fileContent) { // 本地有
      eval(fileContent)
  } else { // 本地没有，再去加载
      let xhr = new XMLHttpRequest();
      xhr.open('GET', url, true);
      xhr.onload = function () {
          let reponseText = xhr.responseText
          eval(reponseText);
          localStorage.setItem(url, reponseText)
      }
      xhr.send()
  }
}
